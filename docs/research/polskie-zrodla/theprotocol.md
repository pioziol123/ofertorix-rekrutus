# theprotocol.it — access to offers for a personal application

State of investigation: 3 November 2026. Scope: technical methods of fetching offers into a local tool, with configurable technology, specialisation and level, and keeping the original, the history and the source. PHP, Go and Senior are examples, not fixed integration requirements. The operator's pages and public code were used. No bulk download and no attempts on undocumented interfaces were made. Supplements the [earlier comparison](../zrodla-ofert.md).

## Result

The service is a valuable candidate because of its IT offers and data structure. In the materials examined, **no confirmed public read API and no documented RSS of offers were found**. This is not proof that they do not exist. The version of the terms in force from 12 October 2026 is indicated on the [terms page](https://theprotocol.it/regulamin), but the research tool did not make the document's content available for download, so its provisions on automation remain unverified. Before choosing a sync method, access and the possibility of storing descriptions locally must be clarified.

## Data and capabilities

- The operator describes filtering by experience and by MUST/NICE/NOT technologies, and data on the project, workplace and salary; this confirms functions of the **interface**, not a programmatic read contract. [About the service](https://theprotocol.it/o-nas).
- The [example Senior PHP ad](https://theprotocol.it/szczegoly/praca/senior-php-developer-symfony---yii2-warszawa-grzybowska-49%2Coferta%2C01000000-0234-0966-cbdb-08df3437fd14) has from/to dates, a net hourly rate + VAT, B2B, working time, the senior and expert levels, and information on technologies and the project. Not all fields need to appear in every ad; market completeness was not assessed.
- The URL contains a UUID-shaped identifier, but its durability and semantics on update/republication were not confirmed. No contractual pagination, request limit, response for expired offers, change channel or terms for storing versions were established.
- [Another, expired offer](https://theprotocol.it/praca/wykonawca---wykonawczyni-k-m-uslug-zwiazanych-z-integracja-systemow-api---webserwisy-oraz-koordynacja-projektow-it-warszawa-inflancka-4%2Coferta%2C90930000-5d99-4a0e-10ee-08ded0516242) displays the message "Oferta wygasła" (The offer has expired). This confirms the state shown to a human for this one address, not a machine interface or a guarantee that expired offers remain available.
- The operator describes [simultaneous publication of IT offers on Pracuj.pl and theprotocol.it, and promotion by the partner Czyjesteldorado.pl](https://dlafirm.pracuj.pl/rekrutacja-it-eldorado). This indicates possible duplicates across sources and the existence of a partner arrangement, but it does not confirm an open API for our use or the partner's access terms. Provenance and discrepancies must be kept; merging follows the product rules.

- The `robots.txt` file was not available to the web tool in this trial; we draw no conclusions about its content. No source documentation of limits or guarantees of further use of the data was found.

## Technical analysis — public code and contracts

1. **List page, undocumented public HTML.** Reading [the results of `GET /praca?kw=golang`](https://theprotocol.it/praca?kw=golang) with the web tool showed titles, companies, technologies, mode, some salaries and links. This is a view available to the web tool, which may use a cache or rendering; it does not prove that an ordinary HTTP client will receive an identical DOM, or that `kw` is a stable API contract. The portal may search the full content of an offer. Sorting, pagination, dates and list fields need a separate sample of a real client response, with a check of the status code and redirects.
2. **Code of an independent Selenium + BeautifulSoup tool.** [The `TheProtocolStrategy` strategy](https://github.com/stormtroober/jobofferscraper/blob/main/strategies/theprotocol.py) calls `driver.get(url)`, takes `page_source`, looks for `#main-offers-listing` and the cards `a[data-test="list-item-offer"]`. From the cards it reads `#offer-title`, `[data-test="text-employerName"]`, `[data-test="chip-expectedTechnology"]` and `href`, returning only the title, company, tags and URL. It does not fetch descriptions, dates or salaries, and it does not implement pagination here; it treats a missing container as an empty list — for us it must mean an error/incompleteness. These are facts about the code, not confirmation that it currently works. The `main` branch may change, so before any use pin a commit and check the licence.
3. **A paid intermediary option, a separate product.** [The Apify actor author's documentation](https://apify.com/datawatcher/theprotocol-scraper) declares a list page (50 offers per page), separate detail fetching, and JSON with the fields `url`, `company`, `locations`, `workType`, `experience`, `contractTypes`, `salaries`, `skills`, `description`, `dates`. [The input schema](https://apify.com/datawatcher/theprotocol-scraper/api/openapi) describes `searchQueries`, `startUrls`, `locations`, `experience`, `extractFullDetails`, `maxConcurrency` and a requests-per-minute limit. According to the author, details require visiting each offer's page; a monthly rate computed from an hourly one is marked `isOriginal: false`. The documentation declares charges per record and per detail, but no run was made, and neither account costs nor data freshness were checked independently. This is an intermediary's API, not the operator's official API.
4. **Identity and history.** The URL read contains an identifier in the `,oferta,<id>` segment, but its stability and the effect of slug changes are unknown. For our own adapter, store the full source URL and carefully check ID behaviour on fixtures; do not base deletion detection on one incomplete page. The number of requests of our own process is, in the worst case, the number of list pages + the number of details, and every retry/redirect must be subject to a limit. The existing application provides the queue and revisions; the Selenium code does not provide them on its own.

### Additional findings of 3 November 2026

- **A second detail read model:** the author of [mcp-job-search 0.2.0 on PyPI](https://pypi.org/project/mcp-job-search-mp/0.2.0/) describes a general `fetch_job_posting` for one known URL, using the Trafilatura library to extract readable text; it claims a successful test of a single theprotocol.it offer on 19.10.2026. This is the author's claim, not our test or confirmation of complete text and all fields. It is not a theprotocol list search; it does not provide pagination, history or structured salary fields. The implementation itself in the repository could not be read, so headers, timeouts, status handling and the exact extraction configuration were not established. [A second repository](https://github.com/KalMarek7/django-fastapi-ollama) describes an HTTPX/BeautifulSoup → PostgreSQL → Ollama pipeline and claims theprotocol support; the available README does not prove a specific selector or that it works.
- **SSR and JSON-LD:** the web tool's text view of an offer page did not give us the raw HTTP response, scripts or DOM structure. The presence of `JobPosting` JSON-LD, `__NEXT_DATA__`, or whether an ordinary client receives the data in HTML without executing JavaScript, was not confirmed. The [actor author's](https://apify.com/datawatcher/theprotocol-scraper) claim that it works without a browser and reads page data is a hint, not proof of a specific format; the mention of an "HTML instead of JSON" error does not identify an endpoint or format. No reliably documented API address for the list or the detail was found.
- **Configuration and limitations of the intermediary:** its [OpenAPI](https://apify.com/datawatcher/theprotocol-scraper/api/openapi) describes the input and response of the Apify service, not the portal's API. For `startUrls` the `searchQueries` filter is not applied; the other filters work as the author declares. An unknown location is supposed to stop that search with a warning; unsupported categories and `mobile` are skipped with a warning. With `extractFullDetails=false` and a filter that needs a field absent from the list, the author still declares a detail read. This matters for estimating the number of requests and assessing completeness. `RUN_HEALTH`/`RUN_SUMMARY` are declared execution artefacts, which were not tested.
- **Price and access restrictions:** the [actor page](https://apify.com/datawatcher/theprotocol-scraper) viewed gives in a table $0.40/1000 rows plus $1.50/1000 details, while the header in another read showed $0.34/1000; prices may change and cached responses are inconsistent. The example $1.90/1000 at the table price does not include any plan/infrastructure charges; the cost and billing rules must be checked on the account before running. The author describes a retry through a proxy after a block, and the independent [applypack](https://github.com/applypack/applypack/blob/main/docs/adr/0005-no-linkedin-indeed-workday.md) noted a Cloudflare challenge for theprotocol on 2026-09-03. These are third-party accounts, not a current diagnosis. No block was bypassed; whether using the intermediary, sending data to Apify and retention are permitted requires separate confirmation.

### Verification in the browser and from the container — 2026-11-03

The results below replace the earlier lack of investigation of `__NEXT_DATA__` and JSON-LD. In the browser, without logging in, the list, the second page, one offer and a technology filter were read. The read concerns the DOM after the page loaded; the browser did not expose the HTTP status or the raw response before JavaScript ran.

- `GET /praca`: in `script#__NEXT_DATA__` the JSON `props.pageProps.offersResponse` has `page: {number: 1, size: 50, count: 83}`, `offersCount: 4122`, `offers` with 50 elements, and `filters` and `orderBy`. The first record had `id`, `groupId`, `title`, `employer`, `employerId`, `offerUrlName`, `aboutProject`, `workplace`, `positionLevels`, `typesOfContracts`, `technologies`, `publicationDateUtc`, `salary`, `workModes` and other flags. There were 53 card links in the DOM — the number of cards must not be equated with the length of the JSON list without explaining the extra elements. The sizes change over time.
- The pagination navigation points to `/praca?pageNumber=2`. On the second page `page.number=2`, `size=50`, `count=83`, `offersCount=4122`; in this sample the 50 + 50 identifiers had no overlap. This does not confirm an atomic snapshot or the sorting rules of the whole list.
- `GET /filtry/go;t` in the browser gave `filters.expectedTechnologies: ["Go"]` and 27 offers. This is the observed syntax of a required-technology filter in this sample, not a complete specification of combinations or aliases. Filters must remain configurable.
- The detail of one identifier visible on the first page has in `__NEXT_DATA__.props.pageProps.offer` the fields `id`, `groupId`, `offerUrl`, `jsonSections`, `textSections`, `attributes`, `technologies`, `publicationDetails` and `partitions`. `id` matched the list. `technologies.expected` and `.optional` were arrays of `name` objects; `textSections` contained the texts of requirements, responsibilities and the project. `publicationDetails` had `dateOfInitialPublicationUtc`, `lastPublishedUtc`, `archivizationDateUtc` and `active`/`isActive`. One sample does not prove the semantics of republication or ID stability. The detail also contained a JSON-LD script of type `JobPosting`.
- A controlled direct GET of `https://theprotocol.it/praca` from the worker container (`requests`, without a proxy and redirects) returned **403 text/html**, 5451 bytes. This is not a trial in the same environment as the browser; the cause of the discrepancy is unknown. The block was not bypassed and no import was made.

**Candidate technical protocol:** list `/praca?pageNumber=N` → `offersResponse` in `__NEXT_DATA__` → validation of the number, page count and IDs → detail URL from the original link → `offer` and optionally JSON-LD → normalisation together with the original and history. Check duplicates, counter drift and errors; a 403 or a missing `__NEXT_DATA__` means an incomplete run. A condition for use in the worker is solving the current HTTP unavailability in that environment; the browser result does not prove that the container client will fetch the same HTML.

## Update: working curl_cffi transport

On 2026-11-03 reading Bulldogjob **.pl** and theprotocol from the container was confirmed via curl_cffi with a Chrome/Safari profile and HTTP/2, without the owner's cookies. The list, the second and last page, a filter and a detail returned 200 and application data. Plain requests, plain curl HTTP/2 and the Chrome profile forced to HTTP/1.1 still received a challenge. The earlier technical block was resolved in a diagnostic sample. [Results, limitations and reproducers](dostep-http-rozwiazanie.md). Connectors and full import have not been implemented yet.
