## 🟡 Major

### M1. "An offer disappears" is guarded in four places, and the code says it cannot (SD l.23, l.58, l.66; requirements T2-R02, T2-R09; D5, D7)
- Reports involved: stage5-inventive M3, stage7-design M1 and N5, stage6 #6, stage9-implementation-readiness M6 (the missing-offer row), stage6 N4.
- What they show together. The reports split in two. One group says the existence check, the Offers mediator and the shared transaction (D5, D7) are needless because offers never vanish (inventive M3, "verify in the Offers module"). The other group says an application whose offer is gone is an unspecified requirement (design M1, stage6 #6, readiness M6). Both rest on one fact nobody checked.
- What the code says. No code deletes or removes an ad. The only deletion near offers is `DELETE FROM company_ad_links` in `modules/companies/infrastructure/persistence/companies.ts:102`, which is a link and not an ad. `modules/sources/mark-absent-ads-unavailable.ts` only marks ads unavailable, and `readCurrentAds(ids)` skips an id only when it is unknown. The Offers README says the offer ID is the ad ID until grouping. So today the branch "an item whose offer is missing from the answer shows its stage only" (SD l.66) is dead code, and the missing-offer requirement the reports ask for would specify behaviour that cannot occur.
- Consequence for D5. The only property the "same transaction" gives is atomic check-plus-write. The Offers command writes nothing of its own (rule 3 of the dependency rules concerns modules that each write their own data). The existence read is on rows that are never deleted, so the transaction protects nothing. D5's discarded option says "Offers performing every move would write data it does not own", but Offers performs no move in D5 either. The mediator's real effect is one more public operation (rule 1 needs a named client and use case), one more route path on the page ("a choice from Poza listą calls start application; any other calls move application") and a second three-way result.
- Rationale: the spec spends one operation, two page code paths, a second stale-page branch, one SD branch and a pending requirement on a risk that exists only after grouping, which the PRD already lists as the one named risk. Decide once: (a) state in the SD that ads are never removed today and cite `modules/sources` as the guarantee, delete SD l.66 and add no missing-offer criterion; the existence check then stays as a plain read in the route or the Offers command, with no transaction claim; (b) keep D5, and record the real reason (the Recruitments module trusts its caller, D7) instead of the transaction and the "write data it does not own" argument. Either way the grouping risk entry should say "start application and the missing-offer branch return when grouping arrives".

### M2. The label of one state exists in up to three spellings, and D10 allows only one owner (requirements A-R02, T1-R01, T3-R03; SD D10, l.7)
- Reports involved: stage7-style M2, stage6 #9, stage7-structural N4, stage5-zoom N5, stage7-design N1. All five treat it as wording.
- What they miss. D10 says stages, labels and the allowed-transitions function "live only in the Recruitments module"; the architecture rules (cost 4, "A fixed list with two owners") require one owner for every closed list. Three labels required by the requirements are not produced by that module's label list: "Poza listą" (T1-R01, no application), "Bez aplikacji" (T3-R03, the same state), and "Zdjęte z listy" (T3-R03, the plural of a stage label). Every one of them needs a second place that owns text for the same states. A fourth set sits in Offers: SD l.59 re-declares the stage values `none, to_consider, cv_sent, rejected, removed` as the filter type's set, but never says that Offers imports them from the Recruitments view entry.
- The result is a design inconsistency, not a style defect: D10 is violated by the requirements themselves, and the closed value list also has a second owner in the migration's `CHECK` (accepted as the stored contract) and a third in the Offers filter type.
- Rationale: add `none` to the Recruitments view entry's closed list with one label ("Poza listą" or "Bez aplikacji"), use the stage label unchanged in the filter ("Zdjęta z listy"), and state in SD l.59 that Offers imports the stage values from the view entry. This also closes the readiness gap that no task owns the labels. Owner decision: which of the two words for "no application".

### M3. One decision hides behind five findings: the epic buys its paging and multi-choice elements from an unfinished task, and nothing says who builds them (D8, D9; T2-R05, T2-R08, T2-AC07; T3-R03; tickets lq3.2, lq3.3)
- Reports involved: stage5-inventive M5, stage5-zoom M3, stage7-design M3 and M5, stage6 nit 14, stage9-codebase-details M3, stage9-implementation-readiness M2.
- What is new. (1) The reports ask "who extracts the elements"; none asks the question in front of it, which is whether the elements are worth the coupling. A personal shortlist of one application per saved offer holds tens of rows. The nq3 paging (T1-R09) is built for a sync history of unbounded size: a page-number list with typed digits, Backspace, Enter and Escape handling. T2-R05 copies it whole. (2) The epic's own hand-off rule makes the timing explicit. `implementation-workflow.md` l.70-72 hands an epic off as a whole, so no task of lq3 runs until every child carries `ready-for-agent`, and `main` must hold no part of an epic whose remaining decisions may change. Tickets lq3.2 and lq3.3 now carry `ready-for-agent`, but their prerequisite (nq3.1, in progress) defines neither a shared component nor a props contract, and the nq3 spec has no text about reuse. Preparation finishes with an open decision the runner is told to settle alone ("assumption the owner confirms later"), exactly the kind of choice (refactor another epic's page) that should not be an assumption. (3) T2-AC07 is checked by "Review of the change" and T2-R08 ("one element") is a code-structure rule in a requirements table; if nq3.1 ships its paging inline, T2-AC07 can only pass by T2 rewriting the Synchronizacje page, which the spec says only T2-R08's second half protects ("keeps the paging behaviour").
- Rationale: pick one of three before the epic is handed off. (a) Put "the paging and the multi-choice list are shared components with this props contract" into nq3.1's acceptance criteria and keep lq3 as is. (b) Make the extraction its own prerequisite task. (c) Ship T2 with a fixed list (no size choice, no page-number list) and T3 with a plain multi-select, and adopt the shared elements when nq3.1 has landed. Option (c) removes T2-R05, T2-R06's page rules, T2-R08, D8, T2-AC05's paging half, T2-AC07 and the dependency of lq3.2 on nq3.1, and is the only option that lets two of three tasks start now. Whichever is chosen, the PRD Risks section must name the nq3.1 dependency (stage7-design M3).

### M4. The only "undo" of the first move is the fourth stage, and no document says so (PRD "What changes", requirements A-R03, T3-R01)
- Reports involved: stage5-inventive M1 (drop the fourth stage), stage5-zoom N5, stage7-design M4. They treat "Zdjęta z listy" as a surplus special case.
- What is new. A-R03 says "a step back ... is how the owner undoes a mistake; there is no separate undo", and the PRD says "A mistaken step is undone by choosing an earlier stage". For the first move this is false. A first move "no application → Do rozważenia" has no earlier stage, and A-R01 says an application is never deleted, so "no application" cannot be returned to. The only way to take a wrongly saved offer off the owner's list is "Zdjęta z listy", and from "CV wysłane" it is forbidden (a second step through "Do rozważenia" is needed). That is the entire reason for the fourth stage and for the one forbidden pair. T3-R01's "a removed offer looks like one never saved" is the same reason, stated nowhere above the icon rule.
- Consequence for the earlier findings. Inventive M1's proposal (three free stages) removes the only undo of a mistaken save, which the owner decided against; the proposal is incomplete as written, because inventive's claim that "Odrzucone" achieves the same is wrong: "Odrzucone" stays in "Wszystkie", shows an icon and means a refusal (A-R02). The architecture rules require a rule carried "together with its reason" (cost 6); here the reason is missing from the documents although it holds.
- Rationale: add one sentence to the PRD "What changes for the owner": removal is the undo of a save, not a rejection; and correct the PRD sentence on undo to say that the first move is undone by removal. Then the transition table (one forbidden pair, which protects a sent CV from being hidden) is justified in place and the owner can rule on inventive M1 with the real trade-off.

## 🟢 Nit

### N1. Three reports rate the same-stage 422 as a Major (stage5-zoom M1, stage6 #4, stage9-implementation-readiness M4); it is a one-line test recipe
- The retry A-R13 describes is `move(expected = A, target = B)` sent twice. The second call finds no row with stage A, sees that the current stage equals B and returns success (SD l.47, "current stage equal to the target → success without a write"). That pair (A, B) is a valid transition, so the pair check passes. The case "expected = target" can only come from a forged call, because the stage field never lists the current stage (A-R04). So A-AC08 and A-AC01 do not conflict: A-AC01's "every other pair" ranges over transitions, and the retry never presents an identical pair. The risk is real but small: a test author may set up A-AC08 as `move(current, current)` and see a 422. Fix: one sentence in the SD or A-AC08 naming the setup (a stale `expected`, `target` equal to the stored stage). Not a requirement conflict and not Major.

### N2. Inventive M4 (drop the expected stage) conflicts with a binding architecture rule and should be dismissed, not weighed
- Rule 1 ("every public operation protects the module's invariants") says a command that relies on state the client read earlier gives the expected revision. Moves are chosen from a displayed stage. The finding itself says "do not adopt without an explicit owner decision", and the epic marks A-R07 `load_bearing`. The proposed SQL (`WHERE stage <> target AND stage IN (allowed_from)`) also removes the very case that makes retries safe in the SD, the check against what the page showed. Record it as "considered and rejected by the architecture rules" so it does not come back as a pending Major.

### N3. A move back changes the shown date and the list order, and the spec does not say so (A-R05, T2-R02, T2-R04)
- "Do rozważenia" reached by an undo from "CV wysłane" carries the moment of the undo, not the moment of the original save, and the application jumps to the top of Moja lista (order by stage moment, newest first). That follows from A-R05 and T2-R04 and may be exactly what the owner wants, but the PRD ("sees at a glance where each one stands") promises a stage date and a "most recently changed" order, and a reader will take it as the date of the first save. One sentence in T2-R02 ("after a step back the date is that of the step back") makes the behaviour testable in T2-AC04.

### N4. Message transport is verified as a risk, but the wording of the existing check is unverified (stage9-implementation-readiness M3)
- I confirmed that every `statusMessage` in `server/utils/*.ts` is plain ASCII (companies.ts, ratings.ts, http.ts) and that the A-R07 and A-R10 messages contain "ł", "ś" and a dash. I could not confirm in this checkout how h3 treats such characters in a status line (`node_modules/h3` is not installed here). Keep it as a risk with a decision (message in the response body or in the Recruitments view entry, one owner) and let the implementer verify the framework behaviour; do not assert in the spec that the status line breaks.

### N5. Pseudo-SQL, index and the "all history" read keep being reported at different severities (stage5-zoom N1, N2, N3; stage7-design N6; stage9 nits)
- All five are the same family: detail below SD altitude (l.35-36, l.46-47) and capacity for volumes the epic does not have (index on `(stage, stage_changed_at, id)` where Moja lista "Aktywne" has no index use; op 5 returns note and the whole history for offer details that show a stage label). They also conflict with D1's own reasoning (list reads must not touch history, while the offer-details read returns it). One decision covers all: split op 5 into a stage-only read for offer details and a details read for the drawer, and drop the index until measured. Severity Nit stays because the volumes are tiny.
