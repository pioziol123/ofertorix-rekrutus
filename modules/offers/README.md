# Offers

The Offers module lets the owner browse job offers: search the list, filter it, sort it and open an offer's details. In the target design it is also responsible for grouping the source ads of the same recruitment into one job offer; this part does not exist yet. This description gives the module's responsibility, the state of its implementation, the public operations, the directory layout and the dependencies. [Domain glossary](../../GLOSSARY.md) · [Module map](../../docs/architecture/moduly.md)

## Responsibility

A **source ad** is an entry on one portal with its own content and change history; the [Sources](../sources/README.md) module fetches and stores it. A **job offer** is a shared employment opportunity, to which several ads of the same recruitment may be linked. The Offers module is responsible for:

- **grouping ads into job offers**: establishing which ads concern the same recruitment, merging offers and splitting them at the owner's command;
- **browsing offers**: a list with view filters, sorting and pagination, offer details with the content change history, and the presentation of salaries, including whether a salary range meets the salary filter.

The module does not assess how well an offer fits the professional profile; that is the Matching module's job. The Offers module uses its result when filtering and sorting the list.

## Implementation state

- **Grouping is not implemented** and does not belong to the epic `oferty-pracy-0mq` (Code architecture fixes). Until then each source ad is shown as a separate offer, and the offer ID is the ad ID.
- **Ads come from the Sources read.** The module reads ads, their content and their versions only through the public read of the [Sources](../sources/README.md#public-read-of-ads) module, which gives the content in a unified form. The module does not interpret the content saved from the source.
- **The match assessment result** in the list comes from the existing Matching read, until task `oferty-pracy-0mq.18`. It reads the current ad versions through the Sources read, and the list makes the same number of database reads whatever the number of offers.
- **The stage of applications** in the list comes from one read of every application's current stage in the Recruitments module (lq3 D3), so the list makes the same number of database reads whatever the number of applications.
- **Filtering happens in memory** on the whole catalogue, which can have at most 10 000 ads; a larger catalogue ends the list read with an error.

## Public operations

The server and other modules import operations from `index.ts`. Views run in the browser, so they have a separate entry `view.ts`, which does not reach into server code.

| Operation                                                                                 | Entry      | Contract                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Read list filters (`parseFilters`)                                                        | `index.ts` | Takes the list query parameters and returns the filters with default values. A value outside the allowed shape raises an error; the API route then responds with code 400. Minimum salary requires a currency and a period. The key `stage` alone takes several values, repeated or comma-separated: `none` for no application and the four stages; an unknown value is left out without an error (lq3 T3-R05).                                                                                                                                                           |
| Offer list (`listOffers`)                                                                 | `index.ts` | Takes the filters and returns a page of 20 offers without the description and history, with the salary match result for each of them, the total number of matching offers, the page number, the applied filters and the filter options gathered from the whole catalogue. A page beyond the last gives the last. Each offer carries a match assessment summary, which the assessment filters and the sort by rating use before pagination, and the stage of its application, absent without one, which the stage filter uses before counting and pagination (lq3 T3-R04). |
| Offer details (`readOffer`)                                                               | `index.ts` | Takes an ID and returns the offer with its current content and the list of content versions from the newest, without the content of earlier versions. An ID that is not a UUID or does not point to an offer gives no result.                                                                                                                                                                                                                                                                                                                                             |
| Start application (`startApplication`)                                                    | `index.ts` | The owner's first move of an offer, which creates its application. Takes the offer ID, the target stage and "now". Checks that the offer exists (`OfferNotFound` otherwise, also for an ID that is not a UUID; its route answers such an ID as invalid input before calling it), then calls the Recruitments module's create application and returns its result; the Recruitments refusals pass through unchanged.                                                                                                                                                        |
| Offers by IDs (`readOffersByIds`)                                                         | `index.ts` | For Moja lista and the application details (lq3 D4). Takes up to 100 offer IDs and returns, in one query, each existing offer's ID, title, company, salary ranges and availability at the source (`OfferSummary`); missing IDs are left out and the order is not defined. More IDs, or one that is not a UUID, raise `InvalidOfferIds`, which its route answers as 422 with the code `invalid_input`.                                                                                                                                                                     |
| Salary text (`salaryLabel`, `salaryOriginLabel`, `salaryTermsLabel`, `salaryPeriodLabel`) | `view.ts`  | The text of a salary range as the offer list shows it: amounts, currency and period, who stated the amount, the contract with net or gross. Every page showing a salary uses it.                                                                                                                                                                                                                                                                                                                                                                                          |
| Filter form query (`offerFilterQuery`, `hasSalaryFilter`)                                 | `view.ts`  | Build the query parameters from the list form, leaving out the salary when that filter is off and a key of several values, the stage filter, comma-separated, and recognise whether a query contains a salary filter.                                                                                                                                                                                                                                                                                                                                                     |
| Stage on the list (`stageFilterOptions`, `readStageFilter`, `listStageIcon`)              | `view.ts`  | For the offer list (lq3 T3): the choices of the filter "Etap aplikacji" with their labels, the reading of the key `stage` of the address, and the stage icon an offer shows, none without an application or in "Zdjęta z listy" (T3-R01). Stages, labels and icons come from the Recruitments view entry.                                                                                                                                                                                                                                                                 |

Both entries also export the offer type (`OfferView`), and `view.ts` the offer summary type (`OfferSummary`); both export the salary type (`Salary`); `index.ts` additionally exports the filter and list page types.

Reads take no locks and run in the caller's transaction, if one is in progress.

## Directory layout

| Place                                                                                                | Contents                                                                                                                                                                           |
| ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `index.ts`, `view.ts`                                                                                | Public entries: for the server and other modules, and for views.                                                                                                                   |
| `list-offers.ts`, `read-offers.ts`, `read-offer.ts`, `read-offers-by-ids.ts`, `start-application.ts` | List, catalogue read, details, offers by IDs and start application operations.                                                                                                     |
| `offer-view.ts`                                                                                      | Offer type: the ad in the unified form of the Sources read with its version history, assessment summary and stage on the list; the offer summary type; the salary type of Sources. |
| `domain/`                                                                                            | Rules on passed data: filters, salary match, the stage filter and icon, filtering, sorting, pagination and filter options, the form query, the salary text.                        |

Unit tests of the rules and a read test on an isolated database live in the module. The test of the API routes and the list page without login is cross-cutting and lives in the shared test directory.

## Dependencies

- **Sources**: the public read of current ads and of the list of an ad's versions. The ad comes with its content in the unified form, including the source name and the assessment of remote work qualification.
- **Matching**: a bulk read of assessment summaries for the list and the list of states awaiting assessment.
- **Recruitments**: create application and the current stages from its `index.ts`, called by start application and the offer list, and the stage values, labels and icons from its `view.ts`. Every later move goes from the pages to the Recruitments module directly.
- **Shared infrastructure**: database access through the shared accessor.

The offer API routes pass the query to the module's operation. The list route adds the source sync state and the match assessment state to the response; until tasks `oferty-pracy-0mq.16` and `oferty-pracy-0mq.18` this assembly stays in the route.
