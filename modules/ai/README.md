# AI

Target architecture of the `modules/ai/` module. The module accepts a request to run AI and exposes its state and result through a provider-independent contract. It is responsible for executor configuration, the queue, handling interrupted executions and the shared budget for paid services. [Module map](../../docs/architecture/moduly.md) · [Cross-cutting requirements](../../docs/specs/lokalne-ai/requirements.md)

## Division of responsibility

| Part              | Responsibility                                                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Requesting module | Prepares the needed data and ties the request to its version. Checks the result by its own rules and decides whether the domain result can be saved or published.                                   |
| Integration layer | Translates a specific use case into an instruction and a response schema. Uses the AI module's public operations and passes the requesting module a unified state and a result in an agreed format. |
| AI module         | Chooses the configured executor, persists the configuration, manages the execution state and settles usage. Exposes the result for domain validation.                                               |
| Executor adapter  | Translates the request, response, errors and usage data. Handles the executor's protocol, e.g. the batch cycle or the agent session cycle.                                                          |

The AI module records the execution state, usage and cost. The execution result is the input to an operation of the requesting module, which applies its own conditions for saving and publishing. The execution state, the settlement and the decision to accept the content are separate.

## Public operations

| Operation          | Contract                                                                                                                                                                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Execution request  | Takes the settings key, the domain operation ID and the prepared input. Returns the execution ID and its initial state, or a defined error.                                                                                         |
| Execution read     | Exposes the state, the result in the agreed format, usage, cost and the cause of an error or of waiting. Reading the history makes it possible to tell apart executions of the same operation.                                      |
| Execution commands | Allow checking, stopping, skipping, resuming or retrying, according to the executor's capabilities and the execution state. Accepting a command means recording the intent. The confirmed effect is visible in the execution state. |
| Budget read        | Exposes the period limit, the reserved and settled amounts and the funds available for new requests.                                                                                                                                |

Public operations hide the queue, the provider's protocol and how the state is stored. A domain operation has its own ID. Each of its executions has a separate ID, and a paid attempt has a separate settlement record.

## Execution modes

| Mode                  | Flow                                                                                                                                                                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Direct model call     | The executor sends one request and receives a response, e.g. from the OpenAI Responses API or Ollama. For the module's client, the execution has an ID and a state.                                                                                |
| Batch at the provider | The executor sends a batch, checks its state and assigns the received results to the individual executions. A valid result of one item can be received even when another item ends in an error. An example is the OpenAI Batch API.                |
| Agent session         | The executor manages the session, observes its progress and collects the result and materials from the provided tools. The agent runs the work loop, and the allowed tools depend on the task. The target local executor uses OpenCode and Ollama. |

The settings of a key choose the provider and model, and the adapters set the allowed execution modes. On a request the module persists the input, the instruction and schema version, and the executor settings and any price list. A pending execution keeps this snapshot after the configuration changes. Secrets are read from the runtime configuration. An unavailable executor or a missing required capability gives an explicit state.

## State and retries

- **Shared local queue.** All local executions use one slot in the installation. The slot stays occupied during work, intervention, waiting for a stop confirmation and when the state is unknown. Releasing it requires confirmation that the specific execution has ended.
- **Recovering work.** After an interruption the module checks the existing execution and resumes receiving the state or the result, if the executor allows it. It records an uncertain submission as a state that needs resolving.
- **Resume and retry.** Resuming continues the same execution. An explicit retry creates a new execution with the saved snapshot of input and settings. The previous result stays in the history, and the previous execution loses the ability to publish. New data or settings require a new request.
- **Execution result and domain result.** When the executor finishes its work, the response can be received. The requesting module checks whether the response belongs to the current execution, whether the input version still allows applying it and whether the content meets the domain rules.

[Queue, session and command contracts](../../docs/specs/lokalne-ai/kontrakty-runtime.md)

## Budget and settlement

- **Reservation.** Before starting a paid attempt, AI reserves funds from the shared budget based on the saved cost configuration. A request without available funds waits for the budget.
- **Settlement.** AI settles an attempt based on confirmed usage. Rejection of the content by the requesting module still allows the incurred cost to be settled. An unknown cost stays reserved until it is clarified.
- **Local execution.** Local inference has zero API cost and is available when the paid budget is exhausted. A paid tool used in a local task requires a reservation. Unknown usage stays an unknown.

The execution history links the state, the cause, the result, usage and artefacts to the execution ID. Diagnostic messages contain only the needed IDs and causes. Input content, raw responses and tool materials have separate access through the execution history, according to the contract of the given mode of work.

## State of implementation

The sections above describe the target module. This section says what the code does today, so a client knows what it can rely on and what is still simpler than the target. The general contract runs single executions with the OpenAI provider and with the local model on Ollama, and provider batches and agent work with OpenAI. The Profile prepares its proposals, Matching its assessments and Companies their research through it.

### Settings and configuration

A client names its executions with a **settings key**: a name it defines for itself, such as `profile`. Under the key AI keeps the client's settings: the provider, the model and the reasoning effort, and nothing else. Everything else is AI configuration: the price list of each model per execution mode, the token caps a reservation covers, the price of a paid tool call and the most calls a reservation covers (agent mode), the provider's secret, the endpoints and the parameters of a local runtime.

| What                                     | Where it lives today                                                                                                                   |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Settings per key                         | [client-settings.ts](client-settings.ts), fixed in code. The keys appear only in this file; no other AI code depends on a key's value. |
| Models, price lists, caps, local runtime | [model-catalog.ts](model-catalog.ts), fixed in code.                                                                                   |
| Provider secret                          | `OPENAI_API_KEY` in the environment.                                                                                                   |
| Endpoint addresses of a local runtime    | `AI_ENDPOINTS_JSON` in the environment.                                                                                                |

AI refuses a request with `not_configured` when the key has no settings, when they are incomplete, or when they name a provider or model AI does not know or a reasoning effort the model does not accept. It does the same when a paid model has no price list for the mode, when the provider's secret is missing, or when the endpoint of a local runtime is not configured. A model with a local runtime has no price list: its inference costs nothing, so nothing is reserved or charged for it. Changing a client's provider or model, or a price, is a code change until the settings move to a table changed through an AI operation.

### Execution states and causes

The public entry point exports two closed lists, the same for every provider. A client chooses its behaviour from the state and the cause alone.

| State            | Meaning                                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `waiting_budget` | In progress: waits until the budget has room for its reservation.                                                                                                                                                                   |
| `queued`         | In progress: waits in the AI execution queue, or for the shared local slot.                                                                                                                                                         |
| `running`        | In progress: the provider is working on it.                                                                                                                                                                                         |
| `delivering`     | In progress: the outcome is saved and waits until the client's receiver takes it over.                                                                                                                                              |
| `completed`      | The client accepted the result.                                                                                                                                                                                                     |
| `rejected`       | The client rejected the result.                                                                                                                                                                                                     |
| `failed`         | Ended without a result, and AI knows how the work ended.                                                                                                                                                                            |
| `uncertain`      | Ended without a result, and AI cannot tell how the work ended. It keeps what it reserved for the work (the budget, or the shared local slot until its process confirms its end); a person checks the execution before trying again. |
| `retried`        | Ended with an error worth another attempt; the next attempt is a new execution of the same operation.                                                                                                                               |

The causes of an end without a result are `refused`, `incomplete`, `no_content` (no single usable content in the response), `format` (content that is not JSON or does not match the response schema, or a response that could not be read), `configuration`, `network`, `http`, `aborted`, `model_unavailable`, `context_overflow`, `adapter_unavailable`, `interrupted` (the work lost its runner while it ran) and `unknown`. Their full descriptions are next to the lists in [execution-state.ts](domain/execution-state.ts).

An execution moves like this:

1. The worker claims a queued execution and calls the provider once. An execution on the shared local slot is claimed only together with the slot, in request order; otherwise it stays queued.
2. AI saves the result, or the end the adapter decided, with the usage and the cost, and sets `delivering`. The cost stays reserved.
3. AI delivers: in one transaction it calls the receiver, settles the cost and sets the final state.

An exception thrown by the receiver is not a decision. The delivery transaction rolls back in full, so none of the receiver's writes and no settlement remain. The execution stays `delivering` with its outcome saved, and the AI execution queue runs the job again (three retries with a growing delay). The provider is not called again. A receiver must therefore accept the same delivery more than once.

The columns `state` and `cause` of the AI executions table are the only record of an execution's stage and of the cause of its end. While an execution is `delivering` an outcome without a result, `end_state` holds the end its adapter decided (`failed` or `uncertain`); the column is cleared when the execution ends, and a database check allows a value only in `delivering`, so a finished execution has no second record of its end. The column `runtime_state` is not a second record of the stage: it is the coordination's observation of the process on the local model. The columns `result_status`, `error_code`, `disposition` and `publication_allowed`, written by the former local Profile path, were moved into `state` and `cause` by a migration, and no code writes or reads them. Removing them belongs to `oferty-pracy-sq2`. The execution's attempt is its settlement record: its state says only whether the cost is still open (its reservation counts against the budget), settled or unknown.

### The shared local slot

All executions of a provider that declares the shared slot (today Ollama) use the installation's one local slot. The slot is held by one execution at a time, under a lease the worker renews every 15 seconds. Before sending, the worker confirms it still holds a live lease, and the raw response is archived with the execution. The slot is released only when the process confirms its end. While the process of an `uncertain` execution has not confirmed its end, the slot stays occupied and the executions behind it wait; a process that never confirms its end holds the slot until a person frees it. Recovery marks the process of a running execution whose lease lapsed as unknown and ends the execution as uncertain through its adapter; it never frees the slot and never sends the request again. When that process later confirms its end, the slot is released, as before, and the execution stays `uncertain`. A process that ends after its lease lapsed, before recovery saw it, also releases the slot: its response is kept in the archive but not delivered, and the execution fails as `interrupted`.

### Provider batches

A client requests the items of one provider batch together, under one group ID it chooses; the budget covers the whole group or none of it. Each item is an execution of its own operation, and the operation ID is the item's identifier at the provider. The items move together:

1. The job of any item takes the group's queued items at once. Only the run that took them has the adapter send the batch; another run finds the group in sending and leaves it to that run.
2. In each recovery cycle, every batch still running gets a job, and its adapter polls the provider.
3. When the batch ended, the outcome of every item is saved with the adapter's state in one transaction, and each item's job delivers its outcome on its own, like a single execution: a delivery that fails is retried without holding back the other items, and a repeated delivery changes nothing.
4. The adapter then removes what the batch left at the provider; recovery retries a cleanup that failed, never the paid submission.

The adapter keeps its own state in the executions' adapter-state column: what it observed of the batch (its files, the provider's batch and status, whether it was cleaned up). The coordination stores and compares that value and never reads it; it is not part of any read. The OpenAI batch adapter archives every file and reply before it reads them, under the group ID, in the batch archive table (`matching_batch_artifacts`, which passed from Matching to AI unchanged). It reads each item's response like a single call; an item without a result ends failed with its cost unknown, unless the provider charges nothing for it (a failed batch without files, an expired request). A batch whose creation the provider did not confirm ends its items as `uncertain` with their reservation kept, and nothing sends it again.

### Agent work

Agent work gathers materials with the allowed tools and writes the result from them. The instruction of the request directs the gathering; the result instruction directs the writing, which gets the JSON object `{"target": <the input>, "evidence": <the materials>}` and answers in the response schema. The tools come from the closed list the public entry point exports (`agentTools`, today `web_search`); a tool outside it is `invalid_request`, and a tool the provider's agent does not offer is `unsupported_mode`, both before anything is reserved. A material is a text with the sources it cites (URL, title, an opened page or a search snippet, the time it was read). ASSUMPTION(oferty-pracy-0mq.22/ASM-3)

1. The worker claims the queued execution and the adapter carries the work out once. Before each step is sent and after its response, the adapter saves its step log (each step's status, response and usage) and the materials in the executions' adapter-state column. A save that fails, because the execution no longer runs, stops the work: nothing more is sent.
2. AI saves the result, or the end the adapter decided, with the usage of the measured steps, and delivers it as any other outcome. The receiver gets the materials with the result; the adapter reads them from its own state.
3. The work is settled as one sum (solution design 0mq.17, decision 6). The attempt records the summed usage of all steps (input and output tokens, calls of the paid tool) and one cost: the summed tokens and the calls at the prices of the agent price list, each of the two rounded up on its own and then added. The usage of each step stays only in the adapter's step log, which the coordination does not read; no cost per step is computed or stored. When a step was sent and its usage is not known, the cost stays unknown and the whole reservation stays held; the usage of the steps that came back is still recorded. The agent price list of a model repeats the token rates, caps and version of its single-mode list and adds the price of a paid tool call and the most calls a reservation covers, so a change of the standard rates is made in both lists (decision 6). ASSUMPTION(oferty-pracy-0mq.22/ASM-4)

The OpenAI agent ([openai-agent.ts](infrastructure/adapters/openai-agent.ts)) runs web search and a synthesis, two calls of the Responses API with a 120-second limit each and the search capped at the tool calls of the price list. Its materials are the paragraphs of the search answer that cite a safe URL; without any, the synthesis is not sent and the work fails with `no_content`. A search still in progress, an HTTP error, a broken connection or an unreadable response leave the work `uncertain`, its cost unknown; a step is never sent again. It runs only models whose price list covers the work (`gpt-6-luna` with an input cap of at least 500000 tokens, `gpt-4.1-mini` with at least 100000 and a fixed block of 8000 input tokens charged per search), with an output cap of at least 4000 tokens and a paid tool; other settings are `not_configured`.

## Adding an execution path

There are two ways to add an execution path. A client that needs AI work for a new job adds a settings key. A new provider or runtime, such as a local model for another job in task `oferty-pracy-334.6`, adds an adapter. Neither changes the modules that already use the contract.

### A new settings key for a client

1. Add the key with its provider, model and reasoning effort to [client-settings.ts](client-settings.ts). The model must be in [model-catalog.ts](model-catalog.ts): with a price list for each mode it runs in, or with a local runtime.
2. In the client's integration layer, translate the request into an instruction, a response schema and the input, and implement a result receiver for the key. The receiver applies the client's rules to a result and records an end without a result, with a message chosen from the state and cause only.
3. Register the receiver where the worker composes dependencies, and connect the AI queue wherever the client requests work.
4. Request work with the check before a request, then the request in the client's own transaction.

The Profile's proposal preparation is the example: [proposal-ai.ts](../profile/infrastructure/adapters/proposal-ai.ts) builds the request and receives the outcomes, and [proposal-preparation.ts](../profile/domain/proposal-preparation.ts) maps each state and cause to the owner's message.

### A new adapter for a provider

An adapter implements the shared adapter contract in [provider-adapter.ts](provider-adapter.ts) and is registered in [provider-registry.ts](provider-registry.ts). It provides:

- **The modes it runs.** Single mode: a function that, given the fixed settings and the request context, returns a model with one call that gives a result and usage or throws a `ModelError`. Batch mode: a function that, given the fixed settings, returns the provider's batch cycle (`BatchRunner`): refusing at request time what one batch cannot take, carrying a group one step further with its own saved state, and cleaning up. Agent mode: a function that, given the fixed settings, returns the agent (`AgentRunner`): whether the settings fit its work, the work carried out once with its state saved step by step, and the materials read from that state. A mode the adapter does not provide is refused at request time.
- **Its translation to public states (`endOf`).** Together with the ends an agent or batch runner returns for its own steps or items, this is the only place where the provider's facts become a public state and cause; all of it is adapter code. Coordination passes the adapter what it observed and saves what the adapter returns: a response the model refused or did not complete, an error the adapter threw, or a lost lease of a running local process. The adapter returns `failed` when it knows how the work ended and `uncertain` when it does not. An `uncertain` end keeps the reservation and the slot.
- **Optional parts.** `check` fixes values before a request, which reach the adapter again as the request context. `ready` says whether its runtime is configured without calling it. `sharedSlot` places its executions on the shared local slot.

The two existing adapters show the mapping:

| What the adapter observed                                | OpenAI                           | Ollama                           |

| A response with no single usable content                 | `failed`, `no_content`           | `failed`, `no_content`           |
| An error before the request was sent                     | `failed`, the error's cause      | `failed`, the error's cause      |
| An error after sending with an end the process confirmed | —                                | `failed`, the error's cause      |
| Any other error after sending; it carries no usage       | `uncertain`, the error's cause   | `uncertain`, the error's cause   |

## Simplifications

The coordination is simpler than the target in the points below. Improvements beyond moving the existing behaviour belong to the epic `oferty-pracy-sq2`.

- **Agent mode on OpenAI only.** OpenAI declares single, batch and agent mode, Ollama single mode only. Agent work on Ollama is refused at request time with `unsupported_mode`, with nothing reserved or queued. Agent work is never retried: an error after a step was sent leaves it uncertain, as research was before.
- **A batch in sending.** A batch whose sending run stopped before the provider confirmed it stays running, and its items cannot get new executions; nothing sends it again. Detecting interrupted sending belongs to task `oferty-pracy-0mq.15`.
- **Delivery after the last retry.** An execution whose receiver keeps failing stays `delivering` with its cost reserved after the queue's retries. Recovery does not deliver it again; a person has to act. Redelivering by hand is a matter for `oferty-pracy-sq2`.
- **No detection of interrupted paid work.** A paid execution whose worker stopped stays running, and its operation cannot get a new execution. Recovery only sends again the jobs of queued executions, funds the ones that wait for budget, and ends a local execution whose lease lapsed. Detecting interrupted work belongs to task `oferty-pracy-0mq.15`.
- **No way to resolve an uncertain end yet.** An `uncertain` local end keeps the shared slot occupied, and nothing in the application frees it. Execution commands (checking, stopping, skipping, resuming, explicit retry) do not exist yet; a person acts in the database.
- **Retries as before.** An error the adapter judges transient gives one more attempt. The OpenAI adapter judges a rate limit or server error with an acceptable wait, and a request that may have been sent without a response, as transient; the coordination reads only that judgement and the suggested wait.
- **Uncertain cost as before.** When the provider was called, any error leaves the cost unknown and reserved unless the adapter reports the usage. Only an execution that no adapter could take settles at zero, because nothing reached a provider: its adapter stopped declaring the mode after the request was accepted, and it ends as failed with the cause `adapter_unavailable`.
- **Schema check.** AI passes the receiver only a result that is JSON and matches the response schema; anything else ends the execution as failed with the cause `format`, and the cost is settled. A response schema AI cannot check is refused at request time with `invalid_request`. The client still validates the content by its own rules.
- **Work of the former Profile paths.** Their queue `profile-ai` has no worker any more. A migration ended their work that had not started (queued, or waiting for budget) as `retried` with the cause `interrupted` and released its reservation; the Profile requests the next attempt through the contract at worker start and in each schedule cycle, which reserves again or waits for budget, with today's prices. Work that was running ended as `uncertain`, keeping its reservation, so nothing that may have been sent is sent again.
- **Work of the former Matching paths.** Their queues `offer-matching` and `offer-matching-group` have no worker any more. A migration gave every assessment made before it an execution with its stage, cause and cost; work in progress (waiting for budget, queued, being sent or submitted) ended as `retried` with the cause `interrupted` and released its reservation, as the owner decided for a system not yet in production. Matching's batch and group tables stay as read-only history.
- **Provider files of the former Matching batches.** The moved executions carry no adapter state, so recovery does not remove at OpenAI the files a former batch left: those of a batch or group that ended while its cleanup had failed, and those of a batch submitted at the deploy. Before the change, cleanup errors were retried. A person can remove them in the provider's panel. The system did not yet run in production (ASSUMPTION(oferty-pracy-0mq.21/ASM-9)).
- **Work of the former research path.** Its queue `company-research` has no worker any more. A migration gave every research made before it an execution in agent mode with its stage, cause and cost; research in progress (waiting for budget, queued or running) ended as `retried` with the cause `interrupted` and released its reservation, as the owner decided for a system not yet in production. Those executions carry no adapter state, so their step log and materials are not kept.
- **Composition.** The AI module registers its built-in adapters itself. The worker connects the queue, registers the Profile's, Matching's and Companies' receivers, resumes the Profile's preparations left by the former path, and runs the queue handler and recovery. The server connects the queue when a profile, matching or research route requests an execution.

The module owns the AI building blocks and a working general contract for single executions on paid and local models, for provider batches and for agent work. Any new guarantee of handling or settlement is a matter for `oferty-pracy-sq2`.
