# Matching

Matching assesses how well an ad fits the owner's confirmed professional profile and justifies the result. [Module map](../../docs/architecture/moduly.md)

## Public operations

Routes, the worker and other modules import operations from `index.ts`. Views run in the browser, so they have a separate entry `view.ts`, which does not reach into server code.

| Operation                                                                                  | Entry      | Contract                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------ | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assessment request (`enqueueMatching`)                                                     | `index.ts` | Requests the assessment of one offer, or reuses the offer's assessment still in progress. A request the module cannot make ends with `MatchingError` and the owner's message.           |
| Group request (`enqueueMatchingGroup`)                                                     | `index.ts` | Takes a command identifier and up to 100 selected offers and places one assignment per offer that needs AI work, all in one save.                                                       |
| Assessments of an offer (`readMatching`)                                                   | `index.ts` | The assessment history of an offer with the state of each request's AI work (and the cost of work of the old way), and its ratings.                                                     |
| Offer-list summary (`decorateMatching`, `matchingListStatus`)                              | `index.ts` | Adds the assessment summary to each offer of a list, in a fixed number of queries; whether groups can be requested, how many assessments are in progress and the most an item reserves. |
| Archive (`readBatchArchive`)                                                               | `index.ts` | What a request's assessment sent to the provider and got back: the exchange of each operation of its assignment, or the archive of its AI work of the old way, read through AI.         |
| Own rating and weights (`manualContext`, `saveManualRating`, `readWeights`, `saveWeights`) | `index.ts` | The form of the owner's own rating and its save, and the group weights with their history and change; a change made meanwhile ends with `RatingConflict`.                               |
| States, labels and weights for views                                                       | `view.ts`  | The states of an assessment and their labels, the groups of the rating, the criterion label, the assessment and weights types and the weights schema.                                   |

## Data

| Data                | Meaning                                                                                                                                                                                                                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assessment request  | One request to assess an ad: the profile version and the ad version it was made for, and the input fixed from them. Its state holds only Matching's meaning: `excluded` (a required condition conflicts, nothing is requested from AI) or `requested`. ASSUMPTION(oferty-pracy-0mq.21/ASM-1) |
| Link to the AI work | A `requested` request keeps the identifier of the assignment placed for it (from task `oferty-pracy-sq2.9`), or, for one requested earlier, is the operation of its AI executions of the old way and keeps the identifier of the first one. Matching stores no cost.                         |
| Outcome             | The published assessment, its calculation, or the owner's message when the AI work ended without an assessment. For a request with an assignment, the receiver saves it, and its presence alone says that the assessment ended.                                                              |
| Ratings and weights | The rating history of each ad (AI, the owner's own and recalculated ones) and the versions of the group weights.                                                                                                                                                                             |
| Read-only history   | The batch and group tables and the attempt link of requests made before `oferty-pracy-0mq.21`. No code writes them.                                                                                                                                                                          |

## Assessments through AI

[assessment-ai.ts](infrastructure/adapters/assessment-ai.ts) translates a request into a single-answer assignment of the AI module, under the settings name `matching`: the instruction, the response format (derived from the assessment contract) and the input. To assess offers Matching uses the AI module's placing of assignments, its status read, its exchange read and its receiver (epic `oferty-pracy-sq2`, task T8); it requests no provider batch and requests nothing through the old way. Whether an offer's assessment is in progress, also one requested the old way, is decided from Matching's own data alone: a request with no saved outcome is in progress (ASSUMPTION(oferty-pracy-sq2.9/ASM-4)). An assessment of the old way whose work ended without its end reaching Matching therefore stays in progress until task `oferty-pracy-sq2.11` ends it. Only the views still read the old way: the state and cost of assessments requested the old way, and the maximum reservation shown (ASSUMPTION(oferty-pracy-sq2.9/ASM-3)).

- **One assignment per offer.** A single assessment places one assignment, labelled with the offer's title and employer, in the save that records the request, and the request keeps its identifier. A group command places one assignment per offer that needs AI work in one save: all are placed or none. The AI module funds each on its own, so the assessments the budget covers run and the rest wait for it; the group stays Matching's concept.
- **Oversized requests** are refused when placed, with nothing saved, when the exact body the paid executor sends is larger than the price list's input cap covers. ASSUMPTION(oferty-pracy-0mq.21/ASM-5)
- **More than 200 criteria** are refused for every request that needs AI work: the assessment contract returns no more, so such a request could never be published. ASSUMPTION(oferty-pracy-0mq.21/ASM-6)
- **The receiver** of assignments (`assessmentAssignmentReceiver`, registered in `receivers/index.ts`) runs in the AI module's transaction that saves the assignment's final status. On a result it checks the assessment against the request's own input (its format, criteria and evidence) and publishes it, or ends the assessment as failed with a safe diagnostic; either way the assignment succeeds. On a failure it ends the assessment as failed with the message of a failed assignment (ASSUMPTION(oferty-pracy-sq2.9/ASM-2)). It changes only a request whose outcome is not saved yet, so a repeated call changes nothing more.
- **What the owner sees** for an assessment with an assignment comes from Matching's own data: "Ocena w toku" until the receiver saved an outcome (also while the assignment needs attention), then "Ocena gotowa", or "Ocena nie powiodła się" ("Błąd oceny" in the offer list). The offer list keeps refreshing while the status read reports an assignment of an assessment of the offers it shows, without an outcome, in progress or needing attention. The exchange view shows the request and raw response of each of the assignment's operations; the cost is in the AI assignments panel.
- **A repeated group command** is recognised from the requests it saved with AI work: their identifiers are derived from the command and the offer (ASSUMPTION(oferty-pracy-sq2.9/ASM-1)). FOLLOW-UP(oferty-pracy-0mq.21/DEV-1): Matching keeps no record of a command's full selection, so a repeated command that saved no request with AI work is handled as a new command. When it only excluded offers, the exclusion is recorded again. When it reused an assessment in progress, a repeat after that assessment ended places a new paid assessment. A changed selection under an accepted command is accepted as a repeat when it differs only in offers outside those requests: it may drop an offer the command reused or excluded, or add an offer whose assessment was in progress when the command was accepted, which is then shown as reused; neither places an assignment. A repeat whose selection shares no offer with those requests, and a repeat of a command accepted before task `oferty-pracy-sq2.9`, are handled as new commands.

**Assessments of the old way.** An assessment requested before task `oferty-pracy-sq2.9` keeps its AI executions until task `oferty-pracy-sq2.11`: its state and cost are read from them, its outcomes still reach the receiver of the old way (`assessmentReceiver`, registered by the AI module plugin), which publishes or rejects a result the same way, and an end without a result gets a message chosen from the public state and cause alone ([assessment-state.ts](domain/assessment-state.ts)). The owner sees such a request's state from its latest execution: waiting for budget, queued, in progress (running or delivering), completed, failed (failed, rejected or retried), needs checking (uncertain), or excluded. ASSUMPTION(oferty-pracy-0mq.21/ASM-3)
